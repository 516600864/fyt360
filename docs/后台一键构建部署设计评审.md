# 后台一键构建/部署 设计评审

> 状态：**待评审**（D先生）｜ 提案日期：2026-10-10 ｜ 关联：决策 #48（站点专属包）、屏 admin-52（站点凭据开通向导）

---

## 一句话结论

推荐 **方案 A：GitHub Actions 云端构建 + 后台触发/部署**——后台点一下即可完成「构建 → 导出 → 落地 → 部署」，零构建机成本；若想先花半天止血，可选方案 C（后台上传模板包）作为过渡。

---

## 1. 背景

现状构建→导出→部署只能在我这里（开发端）跑：

```
本地开发端（唯一入口）
  ① FYT_SITE=site-a npm run build:mp-weixin   ← uni build + 4 个 patch
  ② export-miniprogram-assets.mjs             ← dist 打模板 zip + 完整性断言 + meta
  ③ container-deploy.mjs                      ← 模板随镜像部署到 CloudBase Run
  ④ （可选）hosting-deploy.mjs                ← admin/H5 托管更新
后台唯一动作 = 开通页「下载」模板包
```

问题：改一行文案也要找我开电脑跑全套；部署版本与后台无感知，只能靠 provision.vue 显示的 BUILD 串倒查。

## 2. 目标 / 非目标

**目标**
- 平台超管在后台点「构建」→ 自动出最新模板包并部署，全程无需开发端。
- 版本列表可见（BUILD 串 / 构建时间 / 构建人 / 状态），支持回滚到最近 N 版。
- 全程审计日志（谁在何时触发构建/部署）。

**非目标**
- 不做租户自主构建（模板包是**统一 site-a 基座**，运行时按 X-Fyt-Site 头注入站点，天然单产物；构建是平台动作不是租户动作）。
- 不做 H5/admin 托管的一键化（二期再说）。
- 不改变现有下载端点协议（X-Mini-Pkg-Version / GET meta 不动，客户端零感知）。

## 3. 方案对比

| | A. GitHub Actions 云端构建 | B. CloudBase Run 构建 job | C. 后台上传模板包（半自动） |
|---|---|---|---|
| 核心思路 | 后台调 GitHub API 触发 workflow，CI 内构建+导出，产物回传 COS，后台一键部署 | 后台起临时容器在云上跑 npm build | 本地照常构建，后台网页上传 zip+meta 替换后一键部署 |
| 「构建」也在后台？ | ✅ 全自动 | ✅ 全自动 | ❌ 仅「部署」自动化 |
| 开发工作量 | ~1.5 天 | ~2-3 天 | ~0.5 天 |
| 运行成本 | 0（开源仓 Actions 免费额度足够） | 构建期容器 CPU/内存费 + 依赖安装慢（pnpm 全量 install 冷启 3-5 分钟） | 0 |
| 依赖安装可靠性 | Actions 缓存 node_modules，稳定 | 云内网拉 npm 源不确定 | 不涉及 |
| 构建日志 | GitHub Actions 页面天然可查 | 要自建日志回传 | 不涉及 |
| 风险 | GitHub 触发国内连通性（有波动，需重试）；PAT token 保管 | 重、慢、贵，实现最复杂 | 仍离不开开发端出包 |
| secret 泄漏面 | **零**（构建不需要任何密钥：appid 非敏感，业务凭据全在服务端 DB；PAT 只存服务端 env，不进 CI） | 需要把部署凭据带进构建容器 | 产物人工上传，无 CI 面 |

**推荐 A**；C 可作为 A 交付前的过渡（两者不冲突，C 的上传端点 A 也能复用作人工兜底通道）。

## 4. 方案 A 详细设计

### 4.1 链路

```
[后台 admin] ──点「构建」──▶ [POST /api/admin/build/trigger]
                                 │ 平台超管鉴权 + 并发锁 + 写审计
                                 ▼
                         [GitHub API: workflow_dispatch]
                                 │ （PAT 存服务端 .env，仅 repo scope）
                                 ▼
                    [Actions runner：sync→uni build→patch×4→export→断言]
                                 │ 产物：miniprogram-template.zip + meta.json
                                 ▼
                    [上传 COS build-templates/<build_ver>/…] ──▶ 回调/轮询通知服务端
                                 ▼
[后台「部署」按钮] ─▶ [POST /api/admin/build/deploy] ─▶ 拉产物写 server/assets ─▶ CloudBase Run re-deploy
```

### 4.2 后台界面（挂在现有站点管理页，不新增屏）

「站点管理」页顶部加一条**模板包版本条**：当前线上版本、最新构建版本、三个按钮（构建 / 部署 / 下载）。版本历史抽屉列最近 10 版（版本号、时间、触发人、状态、回滚按钮）。**不新增画布屏**，属于 admin-31 站点管理的增补组件。

### 4.3 关键设计点

1. **并发锁**：Redis 锁 `build:lock`，构建中禁止再触发；部署锁同理（2026-10-09 血泪：container-deploy 禁与 mini build 并行，云上更要串行）。
2. **产物完整性**：沿用 export 脚本既有断言（custom-tab-bar 四件套 / app.js / app.json / bootstrap / vendor / BUILD_VERSION.txt 缺一即 fail）；部署前服务端二次校验 zip + meta.version 一致。
3. **版本留存**：COS 保留最近 10 版，回滚=把历史版本重新走 deploy；本地 server/assets 始终只放当前版（镜像体积不变）。
4. **PAT 保管**：GitHub token 只存服务端 env（`.env`/TCB EnvParams），后台界面永不回显；权限收最小 scope（仅触发本仓 workflow）。
5. **失败处理**：构建失败 → 版本条红标 + 失败原因（Actions conclusion）+ 可重试；严禁静默吞错（E2E 纪律同源）。
6. **site-a 基座铁律**：workflow 构建固定 `FYT_SITE=site-a`（统一基座），杜绝 niwo 污染镜像的可能——这条从流程上根除了 2026-10-09 的 base_code 污染坑。

### 4.4 权限

- 触发构建/部署/回滚：**仅平台超管**（role=platform_admin），复用 requireAdmin 中间件；站点负责人（is_owner）只有下载权。
- 审计：`admin.build.trigger` / `admin.build.deploy` / `admin.build.rollback` 走现有 writeAudit。

## 5. 验收标准（三层实锤，沿用既有纪律）

1. 后台点「构建」→ 5 分钟内版本条出现新 BUILD 串，Actions 日志可回查。
2. 点「部署」→ 线上 `GET /api/admin/sites/site-a/miniprogram/meta` 版本翻转，下载端点 X-Mini-Pkg-Version 一致。
3. 下载包解压实锤：模板四件套齐全、PLUGIN 声明正确（global=[mayi-movie]，pkg-mayi=[ordering,tg]）。
4. 断网/失败演练：PAT 失效、Actions 失败、部署超时三个场景后台均有明确报错不静默。
5. E2E 脚本纳入 verify-site-provision.mjs 同套规矩：可连跑两次全绿。

## 6. 工作量与顺序

| 阶段 | 内容 | 工作量 |
|---|---|---|
| P1 | C 方案上传端点（人工兜底通道，先止血） | 0.5 天 |
| P2 | Actions workflow + 触发/拉取/部署 API + 版本条 UI | 1.5 天 |
| P3 | 版本历史 + 回滚 + E2E | 0.5 天 |

P2/P3 可独立排期；P1 做完后即使 GitHub 波动也有降级通道。
